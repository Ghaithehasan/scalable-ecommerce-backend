# Inventory service

An independent gRPC microservice that owns warehouse stock. It has its own
`package.json`, its own `node_modules`, its own PostgreSQL database and its own
Dockerfile, and it imports nothing from the main application's `src/`. The only
thing the two share is the contract in [`../proto`](../proto).

The main application deliberately stores **no** stock quantity: this service is
the single source of truth for it.

## Contract

`inventory.v1.InventoryService`, defined in
[`../proto/inventory/v1/inventory.proto`](../proto/inventory/v1/inventory.proto):

| RPC | Purpose |
| --- | --- |
| `GetStock` | Batch read of available/reserved levels. Unknown ids are omitted, not an error. |
| `ReserveStock` | Check and reserve every item atomically. Idempotent on `reservation_id`. |
| `ReleaseStock` | Return a reservation's units. Idempotent. |

Two rules shape everything else:

- **`reservation_id` is generated by the caller** (a UUID) before the call.
  That makes retries and compensation safe.
- **"Not enough stock" is a business outcome, not an error.** It comes back as
  `reserved = false` with the shortages listed. gRPC status codes are reserved
  for technical problems.

| Status | When |
| --- | --- |
| `INVALID_ARGUMENT` | missing `reservation_id`, empty `items`, `quantity <= 0`, duplicate product |
| `NOT_FOUND` | a product id this service does not stock |
| `FAILED_PRECONDITION` | `ReserveStock` on a `reservation_id` that was already released |
| `INTERNAL` | anything unexpected (details stay on the server) |

## Running it

### With Docker (recommended)

From **this** directory. The build context is the repository root so that
`proto/` is reachable; the compose file already sets that up.

```bash
docker compose up --build
```

That starts PostgreSQL on host port **5434** and the service on **50051**, runs
the migrations, seeds the stock table, and then starts the server. Stop it with
`docker compose down`, adding `-v` to drop the database volume too.

### Locally

```bash
cp .env.example .env     # defaults already point at localhost:5434
npm install
npm run migration:run
npm run seed
npm run build && npm run start:prod   # or: npm run start:dev
```

| Variable | Default | Meaning |
| --- | --- | --- |
| `GRPC_HOST` | `0.0.0.0` | Bind address |

| `DB_PORT` | `5434` | Chosen so it clashes with neither a local PostgreSQL (5432) nor the main application's database (5433) |
| `DB_USERNAME` | `postgres` | |
| `DB_PASSWORD` | `` | Empty is valid for local trust authentication |
| `DB_DATABASE` | `inventory` | Must never point at the main application's database |
| `DB_STATEMENT_TIMEOUT_MS` | `5000` | PostgreSQL aborts any statement that runs longer |
| `INVENTORY_ARTIFICIAL_DELAY_MS` | `0` | Demo only: makes `ReserveStock` sleep so a client deadline can be shown expiring. Keep at 0 otherwise. |

| `PROTO_DIR` | *(auto)* | Override for the shared proto directory; the Docker image sets `/app/proto` |

The process refuses to start if any of these is malformed.

## Product id mapping

`product_id` is a **string** in the contract so that this service does not
inherit the main application's choice of primary key. The main application uses
integer ids, so it must send `String(product.id)`.

The seed uses fixed ids and never reads the main application's database — doing
so would destroy the database-per-service boundary. The main application has no
seed of its own, so `"1"`..`"8"` are used, matching the ids PostgreSQL assigns
to the first eight products created through `POST /products`.

| `product_id` | `available` | Purpose |
| --- | --- | --- |
| `1` | **1** | The last unit — subject of the race demonstration |
| `2` | 5 | Small stock |
| `3` | 10 | |
| `4` | 25 | |
| `5` | 50 | |
| `6` | 100 | |
| `7` | **0** | Out of stock — shortage scenarios |
| `8` | 7 | |

If your catalogue uses different ids, edit `SEED_ROWS` in
[`src/database/seed.ts`](src/database/seed.ts) and re-run `npm run seed`.

## Calling it by hand

`grpcurl` is not installed on the development machine here and has no npm
distribution, so [`scripts/grpc-probe.ts`](scripts/grpc-probe.ts) (`npm run
probe`) does the same work with `@grpc/grpc-js`. If you do have grpcurl, server
reflection is enabled, so these work as-is:

```bash
# List the services (reflection)
grpcurl -plaintext localhost:50051 list

# Health
grpcurl -plaintext localhost:50051 grpc.health.v1.Health/Check

# Read stock
grpcurl -plaintext -d '{"productIds":["1","2","3"]}' \
  localhost:50051 inventory.v1.InventoryService/GetStock

# Reserve (reservation_id is chosen by YOU, before the call)
grpcurl -plaintext -d '{"reservationId":"11111111-1111-1111-1111-111111111111","items":[{"productId":"2","quantity":1}]}' \
  localhost:50051 inventory.v1.InventoryService/ReserveStock

# Release the same reservation
grpcurl -plaintext -d '{"reservationId":"11111111-1111-1111-1111-111111111111"}' \
  localhost:50051 inventory.v1.InventoryService/ReleaseStock
```

## The race demonstration

```bash
npm run demo:race          # 20 simultaneous buyers
npm run demo:race -- 50    # 50
```

It resets product `1` to a single unit, fires N simultaneous `ReserveStock`
calls with different reservation ids, and prints the outcome:

```
  server      : 127.0.0.1:50051
  product     : "1"
  stock before: available 1, reserved 0
  callers     : 50 simultaneous ReserveStock calls

  result
  ────────────────────────────────  ─────
  reserved = true  (order accepted)  1
  reserved = false (out of stock)    49
  technical errors                   0

  stock after : available 0, reserved 1
  elapsed     : 236 ms

  ✓ Exactly one buyer got the last unit. No overselling.
```

To show the other failure case, stop the service (`docker compose stop
inventory`) and call it again: the client receives `UNAVAILABLE` rather than
hanging.

## Next step: integration notes

None of this is wired into the main application yet. When it is:

**Order flow.** Reserve **before** opening the order transaction. A network
call inside a database transaction holds row locks for the duration of the
round trip and ties the transaction's fate to another service's latency.

```
reservationId = randomUUID()
reserve = ReserveStock(reservationId, items)        ← before the transaction
if (!reserve.reserved) → 409 with the shortages
try {
  order = dataSource.transaction(...)                ← existing code
} catch (error) {
  ReleaseStock(reservationId)                        ← compensation
  throw error
}
```

**Compensation is not optional.** A gRPC deadline only stops the *client*
waiting; the server keeps going and may reserve the units a moment later, for
an order that will never exist. This is verified in
`test/deadline.e2e-spec.ts`. So after *any* failure following a reserve —
including a timeout — the application must send `ReleaseStock` with the same
reservation id. The tombstone and the idempotency rules exist to make that
safe.

**The existing retry loop needs care.** `OrdersService.create` retries the
whole transaction on an `order_number` collision. That loop must retry only the
database transaction, reusing the **same** `reservationId`, and must never call
`ReserveStock` again — the reserve belongs outside the loop.

**Put a deadline on every call.** Without one a client waits forever when the
service is wedged. Something like 2–3 seconds for reserve, shorter for reads.

**Map gRPC statuses to HTTP** in the main application:

| gRPC | HTTP |
| --- | --- |
| `reserved = false` (not an error) | `409 Conflict`, with the shortages in the body |
| `NOT_FOUND` | `404` |
| `INVALID_ARGUMENT` | `400` |
| `FAILED_PRECONDITION` | `409` |
| `UNAVAILABLE`, `DEADLINE_EXCEEDED` | `503`, with a clear "try again shortly" message |
| `INTERNAL` | `500` |

**Convert the id**: `String(product.id)` on the way out, since the contract
uses strings.

**Two things the main application's repository still needs**, both outside the
scope of this work:

- `@nestjs/microservices` added to its `package.json`, with a `ClientsModule`
  pointing at `proto/inventory/v1/inventory.proto`.
- `COPY proto ./proto` in the root `Dockerfile`, so the contract is present in
  the main application's image too. The root `.dockerignore` already keeps
  `proto/` out of the ignore list for exactly this reason.
